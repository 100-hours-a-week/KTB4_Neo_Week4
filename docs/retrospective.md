# Community ERD 회고

## 1. 회고 개요
이번 과제는 단순히 ERD를 그리는 작업이 아니라, 프로젝트의 도메인 모델을 실제 데이터베이스 테이블 구조로 해석하고 왜 그렇게 설계했는지를 설명하는 과정에 더 가까웠다. 처음에는 엔티티 파일에 있는 클래스들을 그대로 테이블로 옮기면 된다고 생각했지만, 실제로는 서비스 로직까지 함께 읽어야 테이블 설계의 핵심이 보였다.

특히 이 프로젝트는 단순 게시판이 아니라 다음과 같은 운영 규칙을 이미 코드에 담고 있었다.

- 회원 탈퇴 후에도 게시글과 댓글의 작성자 연결은 유지해야 한다.
- 게시글 좋아요는 사용자당 한 번만 가능해야 한다.
- 게시글 신고도 사용자당 한 번만 가능해야 한다.
- 조회수는 같은 사용자가 24시간 안에 다시 조회해도 중복 반영되면 안 된다.
- 댓글은 무한 depth가 아니라 대댓글 1단계까지만 허용한다.
- 게시글 수정 시 이전 내용을 이력으로 남겨야 한다.

이 규칙들을 읽고 나서야 ERD가 단순한 "엔티티 그림"이 아니라, 서비스 정책을 담는 구조라는 점이 분명해졌다.

## 2. 설계하면서 중요하게 본 기준
ERD를 설계할 때 가장 중요하게 본 기준은 아래 4가지였다.

1. 각 테이블이 하나의 책임을 가지는가
2. 코드에서 사용되는 비즈니스 규칙을 테이블 구조로 설명할 수 있는가
3. 정규화와 조회 성능 사이의 균형이 맞는가
4. 삭제, 신고, 조회, 댓글 구조 같은 커뮤니티 특성이 자연스럽게 드러나는가

이 기준으로 보았을 때, 엔티티 8개를 각각 `users`, `posts`, `comments`, `drafts`, `post_edit_history`, `post_likes`, `post_reports`, `post_views`로 구성하는 것이 가장 자연스럽다고 판단했다.

## 3. 이번 설계에서 잘했다고 생각하는 점

### 3.1 행위 데이터와 본문 데이터를 분리한 점
가장 먼저 잘했다고 생각한 부분은 게시글 본문과 사용자 행위를 분리한 것이다.

- 게시글 자체는 `posts`
- 좋아요는 `post_likes`
- 신고는 `post_reports`
- 조회 기록은 `post_views`

이렇게 나누면 게시글 테이블이 지나치게 복잡해지지 않고, 사용자별 중복 여부도 명확하게 관리할 수 있다. 특히 좋아요와 신고는 단순 숫자가 아니라 "누가 했는지"가 중요하기 때문에, 별도 교차 테이블로 설계한 것이 맞다고 판단했다.

### 3.2 댓글을 자기참조 구조로 설계한 점
댓글과 대댓글을 굳이 다른 테이블로 나누지 않고, `comments.parent_comment_id`로 자기참조 관계를 둔 것은 구조적으로 단순하면서도 확장 가능한 선택이었다고 본다.

현재 서비스는 대댓글 1단계만 허용하지만, 나중에 요구사항이 바뀌면 서비스 검증만 수정해서 더 깊은 계층으로 확장할 여지도 있다. 즉, 현재 요구사항을 만족하면서도 구조는 과하게 닫아두지 않았다는 점이 장점이었다.

### 3.3 소프트 삭제를 중심으로 본 점
회원, 게시글, 댓글 모두 실제 운영 서비스처럼 소프트 삭제 개념이 들어가 있었다. 이 점을 ERD 설계에서 중요하게 반영한 것이 좋았다.

만약 물리 삭제를 전제로 생각했다면 다음 문제가 생긴다.

- 삭제된 사용자의 게시글 작성자 정보가 끊김
- 댓글 작성자 기록이 사라짐
- 신고/이력/조회 데이터의 추적성이 약해짐

그래서 `deleted`, `deleted_at` 같은 상태 컬럼을 유지하는 방향으로 본 것은 커뮤니티 도메인에 잘 맞는 판단이었다.

### 3.4 비정규화를 무조건 나쁘게 보지 않은 점
처음에는 `posts.likes`, `posts.views`, `posts.comments`가 중복 데이터처럼 보여서 없애는 게 맞지 않나 생각했다. 하지만 서비스 특성상 목록 조회에서 이 숫자들을 자주 읽게 되므로, 원본 테이블에서 매번 `COUNT`하는 구조보다 게시글 테이블에 집계 캐시를 두는 것이 더 현실적이라는 점을 이해하게 됐다.

즉, 이번 과제에서 배운 점은 정규화가 항상 정답은 아니고, 서비스 성격에 따라 의도적 비정규화도 충분히 합리적일 수 있다는 것이다.

## 4. 아쉬웠던 점

### 4.1 엔티티와 물리 모델이 완전히 일치하지 않는 부분이 있었다
ERD를 정리하면서 코드 구조와 물리 설계 관점이 완전히 같지는 않다는 점을 느꼈다.

대표적으로:

- `Post.deletedAt`는 생성 시점에 값이 들어가고 있다.
- `Draft.updateAt`는 네이밍이 다소 어색하다.
- `PostEditHistory`는 엔티티에서 FK 객체가 아니라 `Long postId`만 가지고 있다.

즉, 실행되는 코드 기준으로는 문제 없이 동작하더라도, 데이터 모델링 관점에서는 더 다듬을 부분이 분명히 있었다. 이번 과제는 이런 차이를 발견하는 데 의미가 있었다.

### 4.2 DB 제약만으로 표현되지 않는 규칙이 있었다
댓글 depth 제한처럼, 모든 비즈니스 규칙을 ERD나 DDL만으로 표현할 수는 없었다.

예를 들어:
- 대댓글은 1단계까지만 허용
- 같은 글을 24시간 안에 다시 보면 조회수를 올리지 않음
- 1분에 게시글 3개까지만 작성 가능

이런 규칙은 테이블 설계만으로 끝나는 것이 아니라 서비스 레이어와 함께 설명해야 했다. 처음에는 ERD만 잘 그리면 충분하다고 생각했는데, 실제로는 애플리케이션 로직과 DB 설계를 함께 봐야 과제를 제대로 설명할 수 있다는 점을 배웠다.

### 4.3 인덱스 설계를 더 깊게 검토할 수 있었다
이번에는 기본적인 인덱스 중심으로만 정리했다.

- `posts(deleted, created_at)`
- `comments(post_id, parent_comment_id)`
- `post_edit_history(post_id, created_at)`

하지만 실제 서비스 운영을 기준으로 보면 다음도 더 고민할 수 있다.

- 신고 누적 순 정렬이 필요한지
- 사용자별 내가 쓴 글/댓글 조회가 많은지
- 블라인드된 글만 관리자가 따로 자주 조회하는지

즉, 지금 설계는 과제 기준에서는 충분하지만 운영 환경 수준까지 간다면 쿼리 패턴을 기반으로 인덱스를 더 세밀하게 잡아야 한다.

## 5. 개선해보고 싶은 점

### 5.1 공통 베이스 엔티티 도입
현재는 `createdAt`, `updatedAt`, `deletedAt` 같은 시간이 여러 엔티티에 반복된다. 실제 프로젝트라면 공통 베이스 엔티티를 두고 상속받도록 구성하면 중복을 줄이고 일관성을 높일 수 있다.

### 5.2 상태값 표현 개선
현재는 `deleted`, `blinded`, `published`, `edited` 같은 boolean 플래그가 개별적으로 흩어져 있다. 기능이 더 커지면 상태 조합이 많아져 관리가 어려워질 수 있으므로, 일부는 enum 기반 상태값으로 재설계하는 것도 고려할 수 있다.

예를 들면:
- 게시글 상태: `ACTIVE`, `DELETED`, `BLINDED`
- 임시글 상태: `DRAFT`, `PUBLISHED`

물론 지금 규모에서는 boolean이 단순하고 직관적이지만, 확장성 측면에서는 상태 모델을 조금 더 구조화할 수 있다.

### 5.3 감사 로그 확장
현재는 게시글 수정 이력만 별도로 남긴다. 실제 커뮤니티 서비스라면 다음도 로그화할 수 있다.

- 댓글 수정 이력
- 사용자 정보 변경 이력
- 신고 처리 이력
- 블라인드 처리 사유 및 처리자 기록

과제 수준에서는 과하지만, 운영 서비스 관점에서는 충분히 확장 가능한 영역이다.

## 6. 이번 과제를 통해 배운 점
이번 과제를 통해 가장 크게 느낀 점은, ERD는 단순히 테이블과 선을 그리는 작업이 아니라 서비스의 규칙과 의도를 구조로 번역하는 작업이라는 것이다.

특히 아래 세 가지를 배웠다.

1. 엔티티만 보면 안 되고 서비스 코드까지 읽어야 진짜 제약조건이 보인다.
2. 정규화만 고집하면 실제 조회 성능 요구를 놓칠 수 있다.
3. 소프트 삭제, 교차 테이블, 자기참조 구조 같은 패턴은 커뮤니티 서비스에서 매우 자주 등장한다.

즉, 이번 과제는 ERD 작성 연습이라기보다 "코드를 읽고 데이터 모델을 해석하는 연습"에 더 가까웠다.

## 7. 최종적으로 느낀 점
이번 설계는 현재 프로젝트 요구사항을 설명하기에는 충분히 타당한 구조라고 본다. 특히 좋아요, 신고, 조회 기록을 별도 테이블로 분리하고, 게시글에는 집계 캐시를 남긴 구조는 커뮤니티 서비스 특성에 잘 맞았다. 또한 댓글의 자기참조 구조와 소프트 삭제 설계도 서비스 흐름과 잘 연결되었다.

다만 실제 운영 수준으로 발전시키려면 다음을 더 다듬어야 한다.

- 엔티티 네이밍과 컬럼 네이밍 일관성 정리
- 이력/감사 로그 범위 확장
- 인덱스 세분화
- 상태값 모델 개선
- 동시성 상황에서 집계값 정합성 보강

결론적으로, 이번 과제는 단순히 ERD를 완성하는 것보다, 왜 이런 테이블이 필요한지 설명할 수 있는 설계를 만드는 데 의미가 있었다.
